# 精选编辑案例

用于规则难以落到具体句子时按需查阅。案例示范判断方法，不要求复用措辞；没有说明真实来源的例句均为教学材料，不能作为文章事实引用。稳定规则在对应指南维护，不因一次语感修改继续扩展禁词或替换表。

## 案例一：同一段演示对应不同稿型

**示例材料**：一个生成研究报告的 Agent 在 16 次运行中，有 13 次尝试调用写文件工具。运行配置不允许交互确认，部分日志出现权限错误。材料没有证明这 13 次运行全部失败，也没有证明将提示词写得更明确就一定解决问题。

**不利于解释型公众号的写法**：

> 讲者点开左边的 trace，找到一个 Write Error，再切回代码修改配置。接着他重跑任务、打开另一条记录，发现 Agent 又想写文件。

读者不知道界面里各层是什么，也无法从操作顺序判断问题有多普遍。

**解释型改写**：

> Agent 有时会把生成报告理解为把报告保存成文件。这组 16 次运行中，有 13 次尝试调用写文件工具；配置又不允许交互确认，因此保存操作可能遇到权限限制。这个例子提示，检查报告内容之外，还要核对 Agent 是否执行了预期之外的动作。13 次调用不能直接算成 13 次任务失败。

这里保留结果、证据和适用边界，省掉点击过程。如果原材料没有给出“生成”与“保存”的解释，就只能写观察结果，并把原因作为待验证推测。

**教程处理**：

教程应补齐来源中的 SDK 版本、权限配置、可复现输入、查看工具调用的位置和预期日志。步骤可以是运行来源中的最小示例、核对是否调用写文件工具，再按来源提供的修改重跑，并比较输出与调用记录。必须使用实际来源给出的配置和路径；缺失时说明待补，不能据此虚构可执行教程。

同一段材料，两种目标保留的细节不同。规则见 [文章结构](../article-structure.md#3-现场演示默认直接讲发现证据和意义)。

## 案例二：数量、比率和比较口径

**材料**：某指标的通过数量从 16 次中的 2 次变为 48 次中的 3 次。

**错误概括**：“通过数量增加，说明可靠性提升了。”

**准确概括**：“通过数量从 2 次增加到 3 次，但通过率由 12.5% 变为 6.25%。这两个小样本不足以证明质量稳定下降，却也不支持通过率提高的说法。”

还要核对两组测试的输入分布、设置和指标是否一致。另一项指标全通过，不会自动改变这个指标的结果。规则见 [翻译语义核查](../translation-quality.md#3-翻译必须保留的语义) 和 [比较检查](../sentence-level-errors.md#4-比较对象与数字能否对齐)。

## 案例三：归属不是多余的舞台描述

**材料**：“Lin 把这个内部工具称为‘团队的大脑’，并预测它可能减少协调成本。”

**错误精简**：“这个工具是团队的大脑，将减少协调成本。”

**准确精简**：“Lin 用‘团队的大脑’比喻这个内部工具，认为它有望减少协调成本。”

命名、比喻和预测仍属于 Lin，预测尚未成为结果。如果下一句仍在解释 Lin 的观点，且主体明确，可以不重复姓名；换到另一位发言人的判断或编辑推论时再补归属。规则见 [来源转述与观点归属](../narration-and-formatting.md#来源转述与观点归属)。

## 案例四：更专业的词可能改变事实

**材料**：“团队比较了三种提示词，没有说明随机分配、控制变量或专门的对照组。”

**错误润色**：“团队设置了三个对照组。”

**准确表达**：“团队比较了三种提示词。”

后一句已经清楚，没有必要升级成实验术语。同样，“有实际影响”不能仅为语气有力改成“统计显著”，“同时处理”不能在机制未知时改成“并行计算”。规则见 [句子事实检查](../sentence-level-errors.md#2-句子有没有悄悄增添事实)。

## 案例五：标点检查不能改坏代码与引用

下面代码和链接中的半角标点属于语法，不能批量替换为中文标点：

```python
values = [1, 2]
if values:
    print("ok")
```

[含查询参数的示例链接](https://example.com/watch?v=1&lang=en)

如果来源英文原句是 `The tool may help in this setting.`，中文直引可以写成：

> 作者说（译文）：「在这种设置下，这个工具可能有帮助。」

间接转述则可以写“作者认为，这个工具在该设置下可能有帮助”。两种写法都保留了归属、条件和不确定性。不能去掉引号后仍声称逐字引用，也不能改成“工具会显著改善所有任务”。规则见 [格式规范](../narration-and-formatting.md)。

## 案例六：读者价值不靠添加收益数字

**材料**：工具能复用部分相同输入，未提供成本实验。

**错误补充**：“独立开发者的月账单因此可以减半。”

**有用解释**：“是否能降低账单，取决于输入的重复比例、缓存命中情况和实际计费方式。”

这给出了判断路径，并没有制造量化收益。定义段可以只解释缓存是什么，在后面的章节再讨论适用场景。规则见 [读者价值](../reader-resonance.md#2-在章节或全文层面判断价值)。

## 案例七：标题不能借平台扩大主张

**材料**：嘉宾 Lin 在 Example Channel 的访谈里表示，某工具可能减少自己团队的一类重复任务。

**误导标题**：“Example Channel 宣布：这个工具将取代所有工程师”

它同时改变了观点主体、确定性、作用范围和结果。

**准确方向**：“Lin 如何用工具减少团队的重复任务”适合具体方法得到展开的正文；若只有设想，就用“Lin 对减少团队重复任务的一个设想”。标题能有张力，但不能承诺文章没有证据支持的结论。规则见 [标题策略](../title-and-publishing.md#1-先准确再吸引人)。

## 新反馈怎样进入规则库

先判断反馈指出的是事实错误、稳定的理解障碍，还是当前文章的风格选择。只有能说明触发条件、失误机制和保留例外时，才提炼为通用规则；否则作为局部改写经验，不要求所有文章照搬。

加入案例时保留必要上下文与前后对照，不归档整个历史会话。发现现有规则已经覆盖同一机制时，修改该规则或补一个更好的例子，而不是再增加一条近义禁令。
